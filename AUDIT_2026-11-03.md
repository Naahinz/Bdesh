# Bdesh — Functionality and security audit
**Date:** 3 November 2026  
**Scope:** GitHub frontend, live Supabase database policies and records, Google-only sign-in, learning progression, student profiles, application tracker, college directory, privacy, analytics, and Edge Function.

## Overall result
**Conditional beta.** Static inspection and database access-control checks are complete. A real browser session with two independent test Google accounts is required before unrestricted student access. Do not interpret a clean source check as a successful end-to-end browser test.

## Verified checks
- All nine public-schema tables have row-level security enabled. The student-owned tables enforce `auth.uid() = user_id` on their applicable operations; an authenticated test context returned no foreign-user rows from the student tables.
- All student data remains present. Post-audit totals: 4 application rows, 1 student academic profile, 1 portfolio row, 1 readiness row, 53 published college entries (42 with a review date). These are snapshots, not an indication that every feature has been tested live.
- College editor policies use protected `app_metadata.bdesh_role`; no public student-data read policy grants editor-wide access to other users' private applications.
- Public project code uses a publishable Supabase key, not the service-role key. The deployed `admin-metrics` Edge Function is active with JWT verification and independently checks the authenticated user's protected `app_metadata.bdesh_analytics_admin` privilege.
- No public-schema views were found that could bypass RLS.
- Four college source-note records contained private Gmail evidence references. Original full notes were preserved in `bdesh_private.opportunity_evidence_archive` (schema access revoked from anonymous/authenticated clients, RLS enabled); publicly readable copies were sanitized. A validated CHECK constraint and editor validation prevent these references being reintroduced. The email archive is intended for restricted database administration only.
- Student record exports now invoke `window.URL.createObjectURL` and `window.URL.revokeObjectURL` instead of incorrectly calling these methods on a string constant.
- Lesson progress now uses account-scoped browser storage; the anonymous legacy entry remains separate. The homepage progress ring uses user-owned database state for authenticated users and resets on account transitions. Stale sign-in hydration is guarded.
- Non-final lesson progress failures now surface a warning rather than an unhandled rejected promise.
- Analytics code restricts event names/fields and requires consent, but its public project token is **blank**, so PostHog tracking is **not operating** until configured. Do not describe the admin dashboard as receiving live PostHog events.
- The Supabase security advisor reports leaked-password protection disabled. This is lower priority for the Google-only beta, but review if password-based authentication is later enabled.

## Data-preservation notes
- No student records were deleted, reset, or edited during the audit.
- Original internal university email evidence is preserved in a restricted database archive.
- Existing anonymous learning data remains under its original browser storage key, while new authenticated data is stored under account-specific keys. We intentionally did **not** automatically import anonymous activity into another account.

## Required manual tests before a wider launch
1. **Deployment:** Load `https://bdesh.pages.dev/deployment-check.html`. Confirm all checks pass and browser Network tab shows no 404/stale JavaScript responses.
2. **Two-account isolation:** In the same browser profile, use Google Account A, add a distinct profile entry and complete a lesson. Sign out, log in with Account B. Verify B sees no A data on the homepage progress indicator, learning guide, profile, shortlist or application tracker. Sign out and back into A; confirm A's data returns.
3. **Learning:** Complete a non-final lesson, reload, and verify saved status. Finish the final chapter and confirm redirect to the profile. Disconnect network, mark a lesson and verify the sync warning appears. Reconnect and retry.
4. **Profile:** Save academics and a portfolio activity; reload, edit and remove an activity; confirm only intended items change. Check mobile fields, copying, and PDF printing.
5. **Tracker:** Add a university from the directory, manually add a second, edit application and aid deadlines, change status, tick checklist, add CSS/ISFAA requirements, change submitted/received statuses, reload and confirm persistence. Delete only a disposable test application.
6. **Export:** Download the JSON backup, open it locally, verify its expected fields, and ensure the exported file is not accidentally shared. The workspace backup is not itself a PDF.
7. **Feedback:** Submit a harmless test message and verify actual email receipt; FormSubmit may require initial recipient activation.
8. **Admin:** As an unauthorized Google account confirm the metrics Edge Function returns 403. As an authorized administrator confirm the aggregate dashboard loads and shows no personal account records. Confirm metrics agree with the live database.
9. **Analytics:** If optional PostHog tracking is wanted, set the correct project's **public** token and region, then test: no network analytics before consent, only allowlisted events after consent, no names/essays in payloads, and successful opt-out on the privacy page.
10. **Accessibility / responsive:** Keyboard-only navigation, focus visibility, labels, contrast, mobile-width forms, and expanded university source panels. Include a manual check that the cream/orange glass theme is rendered correctly.

## Deployment caveat
The connected tools could verify source code and live database metadata, but could **not** browse the deployed Cloudflare Pages site or authenticate as test students. Client-side flows and live third-party delivery are therefore **not certified as passing**.

## Recommended release gate
Invite a small supervised beta only after tests 1–6 and the core account-isolation/privacy checks in 8 pass. Complete 7, 9 and 10 before a broader public beta. Keep university aid and admissions information labeled by verification status.
